# OctoAcme Project Management Docs

This repository contains the project management process documents used by OctoAcme. This README provides quick links and a brief overview of the operating rhythm, roles, communication practices, and quality standards that guide work across projects.

## Overall project management approach

OctoAcme organizes work into a clear lifecycle: Initiation, Planning, Execution, Release, and Retrospective. During initiation, teams define the problem, goals, success metrics, stakeholders, and a high-level timeline in a Project One-pager. Planning turns approved initiatives into a prioritized backlog, milestone map, and release plan, with defined owners, acceptance criteria, and a Definition of Done. During execution, the team manages day-to-day delivery through a project board, daily standups, weekly syncs, demos, and structured issue/PR workflows. After release, teams capture lessons learned and convert them into improvement actions so the process continues to improve over time.

## Roles and responsibilities

OctoAcme defines clear roles to reduce ambiguity and improve accountability. Product Managers define outcomes, prioritize the backlog, and measure success. Project Managers coordinate delivery, schedules, risks, dependencies, and stakeholder communication. Developers implement work, write and maintain tests, and collaborate on design and code reviews. QA/testing partners validate quality and acceptance criteria, while stakeholders provide inputs, approvals, guidance, and business context. This role clarity supports better planning, faster decision-making, and more effective execution across teams.

## Communication and quality practices

Effective communication is built into the cadence and documentation. Teams use standups for blockers, weekly syncs for progress and risks, demos for milestone reviews, and planned stakeholder updates to keep decision-makers informed. Shared artifacts such as the Project One-pager, risk register, project board, and release notes act as a single source of truth. Quality is protected through CI checks, security scanning, automated tests, smoke tests for critical flows, manual QA where needed, and a clear Definition of Done. Escalation paths and incident playbooks help the team respond quickly when risks or production issues arise.

## How to use these docs

Use this README as the entry point when onboarding, planning, or revisiting a project. Start with the Overview and Project Initiation docs for new work, move into Planning and Execution for active delivery, and reference Release, Retrospective, and Risk docs during implementation and post-launch learning. Keep these documents updated as the team learns and changes so the process remains clear, repeatable, and useful.
